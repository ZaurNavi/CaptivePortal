# CaptivePortal

[English](README.md) | **Русский**

Универсальная платформа Captive Portal с поддержкой стандартного обнаружения портала и интеграции с контроллерами управляемых гостевых Wi-Fi-сетей.

CaptivePortal реализует полный цикл предоставления гостевого доступа: обнаружение портала, отображение пользовательской страницы, авторизацию клиента, управление сессиями, структурированную телеметрию и эксплуатационный мониторинг.

В настоящее время платформа разрабатывается и тестируется с **TP-Link Omada Software Controller**, однако внутренняя архитектура предусматривает последующее подключение других сетевых контроллеров и механизмов авторизации.

> **Статус проекта:** активная разработка и полевые испытания.

---

## Обзор

CaptivePortal начинался как пользовательский портал для одной гостевой Wi-Fi-сети, но постепенно превратился в модульную платформу, которую можно адаптировать для организаций, предоставляющих публичный или корпоративный беспроводной доступ.

Платформа может применяться в следующих средах:

* парки и общественные пространства;
* гостиницы и объекты гостеприимства;
* офисы и бизнес-центры;
* учебные заведения;
* медицинские и сервисные учреждения;
* торговые объекты;
* площадки для проведения мероприятий;
* муниципальные гостевые сети.

Пользовательский портал отделён от логики конкретного сетевого контроллера. Благодаря этому интерфейс, управление сессиями, телеметрия и мониторинг могут использоваться повторно при интеграции с другим контроллером Wi-Fi или системой управления доступом.

## Текущая интеграция

Первой поддерживаемой интеграцией является:

**TP-Link Omada Software Controller**

В текущем тестовом окружении подтверждены:

* поиск клиентов через Omada Open API;
* авторизация гостей через Omada Open API;
* применение сетевого доступа на стороне контроллера;
* обнаружение портала по стандарту CAPPORT;
* структурированная телеметрия авторизации;
* передача логов в Grafana Loki через Grafana Alloy.

Текущая реализация тестируется с Omada Software Controller ветки **5.14.x**.

Omada является первым контроллерным адаптером, но не постоянным архитектурным ограничением платформы.

## Основные цели

CaptivePortal разрабатывается на основании следующих принципов:

* стандартный механизм обнаружения Captive Portal;
* чёткое разделение логики портала и интеграции с контроллером;
* полная наблюдаемость процесса авторизации;
* предсказуемая обработка ошибок;
* повторно используемая модель сессий;
* независимые от производителя точки расширения;
* поэтапная разработка без одноразовых временных компонентов;
* возможность эксплуатации в реальных гостевых сетях.

## Принцип работы

Текущий процесс авторизации выглядит следующим образом:

```text
Гостевое устройство подключается к Wi-Fi
        ↓
DHCP передаёт CAPPORT-информацию через Option 114
        ↓
Устройство обращается к CAPPORT API
        ↓
Операционная система открывает Captive Portal
        ↓
CaptivePortal создаёт или восстанавливает сессию
        ↓
Backend находит клиента в Omada
        ↓
CaptivePortal отправляет запрос на авторизацию клиента
        ↓
Omada разрешает сетевой доступ
        ↓
Результат авторизации записывается в структурированную телеметрию
```

CAPPORT отвечает за обнаружение портала и передачу информации о состоянии ограничения доступа.

Непосредственное разрешение доступа выполняет интегрированный сетевой контроллер.

## Наблюдаемость

CaptivePortal рассматривает наблюдаемость как одну из основных функций платформы.

События авторизации записываются в виде структурированных JSON-записей и могут содержать:

* идентификатор сессии;
* IP-адрес клиента;
* MAC-адрес клиента;
* номер попытки авторизации;
* результат поиска клиента в контроллере;
* результат авторизации;
* длительность выполнения;
* причину ошибки;
* название модуля и события;
* версию схемы;
* серверную метку времени.

Пример:

```json
{
  "timestamp": "2026-07-28T08:30:15Z",
  "level": "info",
  "service": "captive_portal",
  "module": "auth_telemetry",
  "event": "authorization_succeeded",
  "schema_version": 1,
  "session_id": "example-session-id",
  "client_ip": "192.168.50.24",
  "client_mac": "AA:BB:CC:DD:EE:FF",
  "attempt_number": 1
}
```

Текущий конвейер телеметрии:

```text
CaptivePortal
        ↓
Структурированные JSON-файлы логов
        ↓
Grafana Alloy
        ↓
Grafana Loki
        ↓
Grafana
```

Настройка Grafana и разработка панелей мониторинга выполняются отдельно от кода приложения.

## Архитектура

Проект разделён на несколько логических уровней.

### Уровень портала

Отвечает за:

* отображение Captive Portal;
* визуализацию процесса подключения;
* отображение результата авторизации;
* взаимодействие с backend API;
* обработку повторных попыток.

### Уровень сессий

Отвечает за:

* создание сессий портала;
* восстановление действующих сессий;
* отслеживание попыток авторизации;
* хранение состояния сессии;
* предотвращение конфликтующих операций.

### Уровень интеграции с контроллером

Отвечает за:

* аутентификацию в контроллере;
* поиск клиента;
* авторизацию клиента;
* взаимодействие со специализированным API контроллера;
* нормализацию ответов контроллера.

Первый адаптер предназначен для TP-Link Omada.

В будущем могут быть добавлены адаптеры других контроллеров и систем управления доступом без замены портала и модели сессий.

### Уровень телеметрии

Отвечает за:

* структурированные события приложения;
* диагностику авторизации;
* измерение производительности;
* классификацию ошибок;
* интеграцию с существующим конвейером логирования.

### Интеграционный уровень

Предназначен для входящих событий и внешних систем, включая:

* webhook Omada;
* события жизненного цикла контроллера;
* события отключения клиентов;
* статистику трафика;
* дополнительные инфраструктурные интеграции.

## Подготовка окружения разработки

### Требования

* Linux-сервер или среда разработки;
* Python 3;
* доступ к используемому сетевому контроллеру;
* сетевая доступность контроллера со стороны CaptivePortal;
* DHCP-сервер с поддержкой передачи Option 114.

### Установка

Клонировать репозиторий:

```bash
git clone <repository-url>
cd CaptivePortal
```

Создать виртуальное окружение:

```bash
python3 -m venv venv
source venv/bin/activate
```

Установить зависимости:

```bash
pip install -r requirements.txt
```

Настроить приложение через существующую систему конфигурации:

```text
app/settings.py
app/config.py
```

Запустить приложение:

```bash
python run.py
```

Учётные данные контроллера, адреса, секреты и токены конкретного окружения не должны сохраняться в репозитории.

## Текущая дорожная карта

### Надёжность портала

Планируется:

* ручная повторная попытка без обновления страницы;
* использование существующей сессии при повторе;
* защита от одновременного запуска нескольких процессов авторизации;
* улучшенная обработка задержек DHCP и нестабильной Wi-Fi-связи.

### Клиентская телеметрия

Планируемые события:

* сервер получил запрос страницы;
* frontend-скрипт начал выполняться;
* страница полностью загрузилась;
* страница находилась в видимом состоянии;
* пользовательский интерфейс запустил авторизацию;
* пользователь запросил повторную попытку.

Это позволит различать:

* ошибки загрузки портала;
* ошибки frontend;
* задержки DHCP;
* задержки появления клиента в контроллере;
* ошибки авторизации.

### Интеграция Omada Webhook

Планируется постоянный приёмник webhook Omada в виде отдельного интеграционного модуля.

Первоначальные функции:

* приём webhook-запросов;
* проверка источника;
* сохранение исходного payload;
* запись структурированных webhook-логов;
* сбор реальных данных контроллера для дальнейшего развития.

Последующие этапы могут включать:

* события подключения клиентов;
* события отключения клиентов;
* сбор счётчиков трафика;
* завершение гостевых сессий;
* сопоставление событий с сессиями CaptivePortal.

### Учёт гостевого трафика

Предполагается получать статистику трафика от сетевого контроллера, а не оценивать её по HTTP-трафику самого портала.

Возможные метрики сессии:

* объём загруженных данных;
* объём переданных данных;
* общий объём трафика;
* продолжительность сессии;
* время подключения и отключения;
* точка доступа;
* SSID;
* причина завершения по данным контроллера.

Реализация будет основана на подтверждённых данных Omada Webhook и Open API, собранных во время живого тестирования.

### Поддержка дополнительных контроллеров

В долгосрочной перспективе архитектура может поддерживать:

* другие беспроводные контроллеры;
* авторизацию через маршрутизаторы;
* интеграции RADIUS и CoA;
* управление доступом через firewall или ACL;
* пользовательские адаптеры авторизации.

## Принципы разработки

Проект следует нескольким практическим инженерным правилам:

1. Реальное поведение контроллера проверяется живыми тестами до утверждения архитектуры.
2. Постоянные модули разрабатываются поэтапно вместо создания одноразовых прототипов.
3. Логика конкретного контроллера не должна проникать в универсальное ядро портала.
4. Ошибка телеметрии никогда не должна становиться ошибкой авторизации.
5. Секреты и учётные данные не должны попадать в логи.
6. Каждый этап разработки должен оставлять систему в рабочем состоянии.
7. Эксплуатационные решения должны приниматься по данным телеметрии, а не по предположениям.

## Требования безопасности

Перед промышленным развёртыванием необходимо учитывать требования безопасности конкретной среды.

Предполагаемые механизмы защиты:

* хранение секретов вне исходного кода;
* исключение учётных данных контроллера из Git;
* проверка источника входящих webhook;
* проверка токена или подписи, если она поддерживается;
* ограничение размера запросов;
* rate limiting;
* структурированное журналирование событий безопасности;
* защита от повторяющихся и параллельных операций;
* строгое разделение frontend-данных и доверенного состояния backend.

Значения, переданные frontend, нельзя считать авторитетным источником для:

* статуса авторизации клиента;
* принадлежности MAC-адреса;
* результатов контроллера;
* итоговых значений трафика;
* окончательного состояния сессии.

## Стратегия тестирования

Разработка проверяется в отдельном гостевом VLAN, чтобы изолировать эксперименты от основной сети.

Тестирование включает:

* обычную авторизацию клиента;
* задержку появления клиента в Omada;
* нестабильную беспроводную связь;
* задержки DHCP;
* обновление страницы портала;
* повторные попытки авторизации;
* ошибки API контроллера;
* доставку логов и телеметрии;
* поведение после перезапуска приложения.

Поведение контроллера сначала проверяется живыми тестами, и только после этого реализуются зависящие от него функции.
