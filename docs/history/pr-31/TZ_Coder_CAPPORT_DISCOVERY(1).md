# ТЗ кодеру: предсессионный режим `CAPPORT_DISCOVERY` в существующей странице портала

Статус: готово к передаче Coder  
Дата: 2026-08-04  
Режим выполнения: **CODE-ONLY / DELIVERY-AS-TEXT**

## 1. Цель

Устранить ошибку, которую видит посетитель, когда `/capport/login` уже открыт, но Omada ещё временно не показывает подключившееся устройство.

Нужно расширить жизненный цикл существующей `portal.html` назад: до появления `AuthSession` эта же страница должна работать в режиме ожидания обнаружения клиента, а после обнаружения — продолжать уже существующий поток авторизации.

Отдельную страницу `capport_wait.html` создавать и использовать запрещено.

## 2. Принятое архитектурное решение

Используется одна страница `portal.html` с тремя режимами:

1. `CAPPORT_DISCOVERY` / `DISCOVERING_CLIENT` — Omada ещё не показывает клиента, `session_id` отсутствует.
2. Обычный существующий режим `AUTH_SESSION` — клиент найден, создана настоящая `AuthSession`, работает текущая авторизация.
3. Существующий контролируемый `FAILED` — отображается ошибка и штатный retry, если он предусмотрен текущей реализацией.

Новый режим не является вторым механизмом авторизации. Он только повторяет вход в существующий CAPPORT-flow до того момента, когда можно безопасно вызвать существующий `open_portal()`.

## 3. Текущее нежелательное поведение

Последовательность, которую требуется исправить:

```text
телефон открывает /capport/login
→ Omada временно не находит устройство
→ посетитель получает техническую ошибку
```

Требуемая последовательность:

```text
телефон открывает /capport/login
→ Omada временно не находит устройство
→ сервер возвращает portal.html в режиме CAPPORT_DISCOVERY
→ страница не обращается к AuthSession API
→ раз в 2 секунды повторяется /capport/login
→ Omada находит устройство
→ вызывается существующий open_portal()
→ создаётся настоящая AuthSession
→ та же portal.html продолжает обычную авторизацию
```

## 4. Разрешённая область изменений

Работать только с актуальными версиями переданных файлов:

- `app/capport/routes.py`;
- `app/web/templates/portal.html`;
- существующий файл целевых тестов CAPPORT, ожидаемый путь — `tests/test_capport_routes.py`.

Если фактический тестовый файл называется иначе, использовать уже существующий файл тестов маршрутов CAPPORT. Новый тестовый каталог и новую тестовую инфраструктуру не создавать.

Новые production-файлы не создавать.

## 5. Серверная логика `/capport/login`

### 5.1. Временное отсутствие клиента

Только существующий результат, означающий «клиент временно не найден в Omada», переводить в `CAPPORT_DISCOVERY`.

Нельзя превращать в ожидание:

- невалидный или недоверенный source IP;
- ошибки валидации входа;
- недоступность контроллера;
- ошибки аутентификации Open API;
- внутренние исключения;
- любые другие ошибки, которые текущая реализация считает контролируемыми или terminal.

Для `CAPPORT_DISCOVERY`:

- вернуть HTTP `200`;
- рендерить существующую `portal.html`;
- передать `session_id = null` / `None`;
- не создавать `AuthSession`;
- не запускать `AuthWorker`;
- не выполнять authorization POST;
- сохранить текущую проверку guest source IP;
- установить `Cache-Control: private, no-store`;
- установить `Pragma: no-cache`.

Минимальное состояние discovery:

```python
{
    "state": "DISCOVERING_CLIENT",
    "status": "DISCOVERING_CLIENT",
    "mode": "CAPPORT_DISCOVERY",
    "progress": 5,
    "terminal": False,
    "retryable": True,
}
```

Допустимо аккуратно адаптировать форму этого объекта под фактический контракт `portal.html`, но имена `DISCOVERING_CLIENT` и `CAPPORT_DISCOVERY` должны остаться однозначными.

Каждый render `portal.html` должен получать полный существующий контракт шаблона. Включая controlled-error и discovery, передавать фактические существующие аналоги:

- `session_id`;
- `initial_state`;
- `portal_translations` / `PORTAL_TRANSLATIONS`;
- `redirect_url`;
- новые параметры bounded discovery, перечисленные ниже.

Не создавать второй набор переводов и не копировать существующую авторизационную логику.

### 5.2. Ограниченный цикл ожидания

Один автоматический цикл длится не более `60` секунд по часам сервера.

Использовать один параметр серверного дедлайна, например существующий `wait_until`, в Unix seconds.

Правила:

1. Параметр отсутствует — сервер начинает новый цикл и устанавливает дедлайн `server_now + 60`.
2. Параметр корректен и находится в будущем — сохранить тот же дедлайн.
3. Параметр истёк — не создавать новый дедлайн, установить `auto_retry = False`, остановить автоматические переходы и показать кнопку «Повторить».
4. Параметр больше `server_now + 60` — ограничить его значением `server_now + 60`.
5. Синтаксически некорректный параметр обработать без исключения. Допустимо считать его отсутствующим и создать один новый ограниченный цикл; сформированный сервером `retry_url` после этого обязан содержать уже корректный ограниченный дедлайн.
6. Автоматический запрос всегда должен переносить один и тот же валидированный дедлайн. Он не должен продлевать сам себя после каждого reload.

Сервер должен передать шаблону:

- `retry_url` — безопасный URL повторного `/capport/login` с сохранением необходимых исходных CAPPORT-параметров и валидированным `wait_until`;
- `restart_url` — тот же безопасный вход без `wait_until`;
- `auto_retry`;
- `retry_interval_ms = 2000`;
- `remaining_seconds`, рассчитанный сервером и ограниченный диапазоном `0..60`.

URL должны строиться серверным способом, принятым в проекте. Нельзя конкатенировать в JavaScript непроверенные query-параметры или доверять URL, присланному клиентом.

### 5.3. Клиент обнаружен

Если очередной запрос уже находит клиента:

- немедленно перейти в существующий `open_portal()`;
- не создавать отдельный authorization-flow;
- не менять существующий формат ключей `AuthSession`;
- не менять существующие состояния, polling и retry обычной авторизации;
- не переносить discovery-дедлайн в `AuthSession`.

## 6. Изменения в `portal.html`

Сохранить существующие:

- дизайн и трёхцветный фон;
- карточку и брендинг `Zəfər Parkı`;
- текущий переключатель AZ/RU/EN;
- обычную анимацию и прогресс;
- существующий AuthSession polling;
- существующие success/failed состояния.

Добавить отдельную ветку JavaScript для `CAPPORT_DISCOVERY`.

Логика запуска:

```text
есть настоящий session_id
→ выполнять существующий AuthSession polling без изменения

session_id отсутствует и mode == CAPPORT_DISCOVERY
→ не обращаться к AuthSession endpoint
→ показывать подготовку подключения
→ при auto_retry=true через 2000 мс выполнять location.replace(retry_url)
→ при auto_retry=false остановиться и показать кнопку «Повторить»

session_id отсутствует и это controlled FAILED
→ сохранить существующее отображение ошибки
```

Обязательные требования:

- не формировать Unix timestamp в браузере;
- не сравнивать дедлайн с `Date.now()`;
- для локального обратного отсчёта использовать `remaining_seconds` и `performance.now()` либо локальное уменьшение переданного значения;
- сервер остаётся источником истины дедлайна;
- автоматические переходы выполнять через `location.replace()`;
- кнопка «Повторить» открывает `restart_url` без `wait_until` и сама не рассчитывает время;
- при отсутствии `session_id` ни при каких условиях не формировать URL вида `/auth/session/...` и не запускать session polling;
- после переключения в обычный режим не должны оставаться discovery timers;
- не добавлять второй CSS, вторую карточку или второй языковой переключатель.

Добавить короткие пользовательские тексты для AZ/RU/EN через существующий механизм переводов. Язык по умолчанию и его выбор не менять. Смысл текстов:

- заголовок: «Подготавливаем подключение»;
- пояснение: «Ожидаем появления устройства в сети»;
- кнопка: «Повторить».

Формулировки на азербайджанском и английском должны быть естественными, без технических слов `Omada`, `AuthSession`, `MAC`, `polling` или `CLIENT_NOT_FOUND`.

## 7. Error handling и безопасность

- Не показывать пользователю traceback или внутренний error code.
- Не логировать tokens, secrets и полный raw response контроллера.
- MAC не маскировать, если существующая telemetry его пишет.
- Не добавлять infinite retry.
- Не ослаблять guest source IP validation.
- Не менять token lifecycle общего OmadaProvider.
- Не подавлять реальные ошибки контроллера под видом `DISCOVERING_CLIENT`.
- Не добавлять внешние зависимости.

Существующее логирование маршрута сохранить. Допустимо добавить только компактные существующему формату события начала/истечения discovery, если для этого уже есть готовый механизм. Новую подсистему логирования не создавать.

## 8. Минимальные тесты

Добавить только четыре целевых тестовых сценария в существующий файл CAPPORT route tests. Допускается объединение близких случаев через parametrization.

1. **Временный client-not-found**  
   Ответ `200`, присутствует `CAPPORT_DISCOVERY`, выставлены `private, no-store` и `no-cache`, `session_id` отсутствует; mocks подтверждают, что `AuthSession` и worker не созданы.

2. **Истёкший дедлайн**  
   При фиксированном server time просроченный `wait_until` не заменяется новым, `auto_retry = False`, автоматический reload отсутствует, отображается кнопка повторного запуска.

3. **Валидный и чрезмерно далёкий дедлайн**  
   Валидный будущий дедлайн сохраняется между запросами; значение дальше `now + 60` ограничивается. Можно реализовать одним параметризованным тестом.

4. **Клиент появился**  
   Повторный запрос использует существующий `open_portal()` и обычный AuthSession-flow; discovery-ветка больше не активна.

Требования к тестам:

- не обращаться к реальной Omada;
- не выполнять реальные ожидания 2 или 60 секунд;
- фиксировать server time через существующий проектный mock/monkeypatch;
- не добавлять browser/E2E framework;
- не переписывать и не ослаблять существующие тесты;
- не запускать полный test suite.

Если у Coder есть исполняемое окружение, выполнить только:

```bash
python -m pytest -q -rs tests/test_capport_routes.py
python -m compileall -q app
```

Если фактический путь тестов отличается, первую команду скорректировать только на реальный существующий CAPPORT test file.

Если окружения нет, ничего не имитировать и прямо написать `TESTS NOT RUN — execution environment unavailable`.

## 9. Не входит в задачу

- создавать или использовать `capport_wait.html`;
- внедрять код на сервер;
- менять systemd или `.env`;
- настраивать Omada Controller;
- менять OmadaProvider и его token cache, кроме уже существующего вызова через route;
- менять `AuthSessionManager`, `AuthWorker` или authorization POST;
- менять Pending Client Session Cleaner;
- менять Visitor Registry, Snapshot Collector или webhook normalizer;
- менять Grafana, Alloy, Loki и dashboard JSON;
- добавлять dependencies;
- выполнять общий рефакторинг;
- исправлять посторонние дефекты;
- создавать документацию проекта или ADR в рамках этой правки.

## 11. Формат результата Coder

Предпочтительный результат — один передаваемый файл:

```text
candidate_capport_discovery.patch
```

Это должен быть обычный unified patch **как текстовый формат доставки**, а не результат Git-операции. Он должен содержать изменения только трёх разрешённых файлов: двух production-файлов и существующего CAPPORT test file.

Если платформа Coder не умеет прикладывать файл, вывести полный patch прямо в ответе одним fenced code block.

Если Coder не может надёжно сформировать patch, резервный формат:

1. полный готовый текст `app/capport/routes.py`;
2. полный готовый текст `app/web/templates/portal.html`;
3. полный готовый текст фактического CAPPORT test file.

Не отдавать только отдельные фрагменты без точного места вставки. Не отдавать псевдокод.

После кода приложить короткий handoff:


Не включать длинное описание рассуждений, посторонние рекомендации или упоминания Cleaner/token invalidation, если они не относятся к представленному коду.

## 12. Критерии приёмки

Работа Coder готова к нашему review, если одновременно выполнено всё следующее:

1. Используется только существующая `portal.html`.
2. При временном отсутствии клиента возвращается HTTP `200`, а не `400/404/500`.
3. До обнаружения клиента нет `AuthSession`, worker и authorization POST.
4. Страница без `session_id` не опрашивает AuthSession endpoint.
5. Автоматический retry выполняется каждые 2 секунды и ограничен 60 секундами server time.
6. Истёкший дедлайн не создаёт новый цикл автоматически.
7. Клиентский код не использует часы телефона для серверного дедлайна.
8. Кнопка «Повторить» начинает новый цикл через URL без `wait_until`.
9. При обнаружении клиента вызывается существующий `open_portal()`.
10. Обычная авторизация, success, failed и перевод интерфейса не сломаны.
11. Нет новой production-страницы, зависимости или отдельного authorization-flow.
12. Добавлены только минимальные целевые тесты.
13. Результат передан кодом/patch-файлом без Git/GitHub и без внедрения.

## 13. Stop conditions

Coder должен остановиться и описать несовпадение, не придумывая новый контракт, если:

- в актуальных исходниках нет `portal.html` или `/capport/login`;
- фактическая точка входа не использует `open_portal()`;
- непонятно, какой существующий outcome означает временный client-not-found;
- для решения требуется менять `AuthSessionManager`, `AuthWorker`, OmadaProvider public contract или более трёх разрешённых файлов;
- переданные исходники явно не совпадают между собой по версии.

В этом случае код не расширять за пределы ТЗ; вернуть найденное несовпадение и список минимально необходимых дополнительных файлов.
