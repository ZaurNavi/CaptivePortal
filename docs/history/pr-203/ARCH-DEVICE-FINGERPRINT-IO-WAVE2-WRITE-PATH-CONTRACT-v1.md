# 4. FP-W2-01 — BOUNDED INGRESS COALESCING

## 4.1 Exact scope

Coalescing is permitted only for:

```text
endpoint = evidence
```

It MUST NOT delay:

```text
endpoint = source_health
```

A source-health event is a flush barrier.

Therefore the coalescer never creates a mixed evidence/source-health durable transaction.

## 4.2 Exact production candidate caps

If enabled:

```text
MAX_EVENTS = 32
MAX_OLDEST_EVENT_WAIT_MS = 100
MAX_BUFFERED_SERIALIZED_BYTES = 262144
```

These are architecture constants, not operator-tunable production values in v1.

Lab MAY benchmark:

```text
50 ms
100 ms
250 ms
```

but only the exact `100 ms / 32 / 256 KiB` profile is eligible for the first production candidate under this contract.
A different production value requires architecture return.

The existing durable spool transaction hard maximum remains:

```text
MAX_TRANSACTION_ROWS = 100
```

Wave-2 coalescing does not raise it.

## 4.3 Ordering

Every submission to the coalescer receives a process-local monotonic submission ordinal under one synchronization boundary.

Flush order is that submission order.

Within each input call, original event order MUST be preserved.

Cross-thread ordering is the order in which submissions enter the coalescer synchronization boundary.
No event-time sorting is allowed.

The existing downstream endpoint-homogeneous HTTP batching semantics are unchanged.

## 4.4 Flush triggers

Pending evidence MUST be flushed immediately when the first applicable condition occurs:

```text
1. pending count reaches 32;
2. oldest pending event reaches 100 ms monotonic age;
3. pending serialized size would exceed 256 KiB;
4. a source_health event is submitted;
5. runtime begins orderly shutdown;
6. raw/EVE worker exits because of an exception;
7. source-health transition is about to be emitted;
8. spool.capacity_blocked becomes true;
9. coalescer itself enters fallback mode.
```

A single event larger than the coalescer byte ceiling bypasses coalescing and uses the legacy immediate enqueue path, still subject to existing spool/Task-01 limits.

## 4.5 Stalled traffic

A dedicated bounded flush timer/condition MUST ensure that an event is not left pending merely because no later packet arrives.

```text
oldest pending age >= 100 ms
→ flush without waiting for another source event
```

No busy loop.

## 4.6 Shutdown

Orderly shutdown:

```text
stop accepting new raw/EVE input
→ close capture / EVE receiver
→ join producer loops
→ flush pending evidence once
→ stop coalescer/timer
→ continue existing delivery-worker shutdown
→ close spool
```

The existing total Sensor shutdown budget remains 20 seconds.

If the final flush cannot complete within the existing shutdown budget:

```text
shutdown is NOT reported clean
```

No forced ACK and no timestamp rewriting are allowed.

## 4.7 Exception/fallback behavior

If the coalescer logic itself fails while the spool is still operational:

```text
1. disable coalescing for the rest of that process lifetime;
2. attempt one bounded legacy enqueue of the pending events using their existing IDs;
3. subsequent events use the legacy immediate enqueue path;
4. emit sanitized operational fault telemetry.
```

If the underlying spool write itself fails, existing SensorSpool failure/capacity semantics remain authoritative.

A fallback retry may re-submit the same event IDs; `INSERT OR IGNORE` / central idempotency must keep this safe.

## 4.8 Crash envelope — explicit

The accepted Task-02 guarantee remains absolute for events already committed to SensorSpool.

When coalescing is enabled, process/power crash **before the coalesced batch reaches the durable spool commit** may lose only the process-local pending set:

```text
at most 32 evidence events
and
at most 100 ms of pre-durable evidence age
and
at most 256 KiB serialized pending evidence
```

Source-health transitions are not intentionally held in this window.

This is a real failure-envelope change compared with immediate enqueue and MUST NOT be described as zero-loss.
Production activation of ingress coalescing therefore requires the explicit Owner exception in §15.

# 5. FP-W2-02 — PROOF-GATED STALE PURGE

## 5.1 Goal

Avoid executing the current bounded stale DELETE path on every `enqueue()` / `batch()` call when it is already provable that no stored row is stale.

The 24-hour stale semantics themselves do not change.

Exact existing comparison remains:

```text
observed_at < now_utc - 86400s
→ stale

observed_at == now_utc - 86400s
→ still eligible
```

Incoming events MUST still be age-checked on every enqueue even when stored-row purge is skipped.

## 5.2 Conservative cache

Process-local cache:

```text
next_possible_stale_at_utc: timestamp | EMPTY | UNKNOWN
```

Meaning:

```text
UNKNOWN
= no proof exists; stale scan required

EMPTY
= DB was observed empty at the last authoritative refresh

TIMESTAMP
= no currently known stored row can become stale before this UTC instant
```

This cache is not persisted and is not product evidence.

## 5.3 Rebuild / invalidation

On process/spool initialize:

```text
cache = UNKNOWN
```

The first purge decision performs a read-only:

```sql
SELECT MIN(observed_at) FROM sensor_spool
```

If no row:

```text
cache = EMPTY
```

Else:

```text
next_possible_stale_at_utc = min_observed_at + 86400s
```

New inserts may only move the deadline earlier:

```text
cache = min(existing_deadline, inserted_event.observed_at + 86400s)
```

ACK/eviction/deletion is allowed to leave an earlier conservative deadline in cache.
That can cause an unnecessary future scan but can never extend retention.

After a real stale-purge pass, refresh the cache from the surviving DB minimum.

## 5.4 Exact skip predicate

Stored-row stale DELETE may be skipped only if:

```text
cache is EMPTY
OR
(cache is TIMESTAMP AND now_utc < next_possible_stale_at_utc)
```

Otherwise run the existing bounded purge behavior.

If cache parsing/state is invalid:

```text
cache = UNKNOWN
→ run legacy purge
```

Never fail open by assuming "no stale rows".

## 5.5 Clock discontinuity

Clock rollback:

```text
now moves backward
→ existing earlier deadline remains conservative
→ no retention extension beyond the same current local-UTC contract is invented
```

Clock forward:

```text
now >= cached deadline
→ stale purge becomes mandatory before skip may resume
```

No monotonic clock substitutes for the accepted wall-clock age decision.

## 5.6 Explicit purge / capacity pressure

An explicit maintenance/test `purge_stale()` request always executes the purge path regardless of the cache.

Capacity enforcement remains allowed to force a stale check.

## 5.7 Capacity cache — rejected

Wave 2 v1 MUST NOT replace these current authoritative checks with a cached estimate:

```text
row count
physical main DB size
rollback journal size
configured max_events
configured byte/headroom budget
capacity_blocked recovery
```

The current code already performs actual eviction DELETE only when row/byte pressure exists.
Those read checks remain because they do not create the write semantics this optimization is trying to remove.

# 8. FP-W2-05 — FINGERPRINT EVIDENCE SINK

## 8.1 Current exact write semantics

At the pinned baseline:

```text
fingerprint-evidence.service
Task-01 repository
journal_mode=WAL
synchronous=NORMAL
```

For one accepted HTTP evidence/source-health request:

```text
validate full request
→ BEGIN IMMEDIATE
→ read shared ingest watermark
→ per producer-event identity:
     detect existing row
     exact immutable equality => duplicate_noop
     different immutable payload => conflict
     new => insert
→ update shared last_ingest_sequence only if at least one row inserted
→ COMMIT
```

The Sensor currently sends at most 100 events per HTTP batch.
Therefore the server-side evidence sink already has one DB transaction per Sensor delivery batch, not one transaction per evidence row.

## 8.2 Additional bulk insert

Wave 2 v1 decision:

```text
NOT AUTHORIZED / NOT JUSTIFIED AS WRITE-IO FIX
```

Replacing the row loop with `executemany()` does not by itself reduce the durable COMMIT count.
It may be a CPU/SQL-call optimization, but that is not the current architecture target.

## 8.3 Duplicate read shortcut

A speculative pre-transaction "all duplicates" shortcut is not admitted in Wave 2 v1.

Reason:

```text
current write transaction is the semantic owner of:
immutable conflict checking
shared ingest-sequence allocation
concurrent ingest serialization
```

Before changing that boundary, profiling must show that duplicate-only requests are a material write-I/O source.

## 8.4 Allowed work in F3


# 9. FP-W2-06 — SENSOR TELEMETRY AGGREGATION

## 9.1 Audit classification

Routine per-batch:

```text
fingerprint_delivery_completed
```

and routine Suricata stats log emission are operational telemetry, not canonical evidence/audit records.

Canonical evidence remains Task-01 DB + durable spool/Task-01 identity semantics.

Therefore routine success/stat logging MAY be aggregated.

## 9.2 Exact 60-second aggregation

When enabled:

```text
window = 60 seconds monotonic
```

Do NOT emit one journald line for every successful delivery.
Accumulate in memory:

```text
delivery_success = sum(delivered events)
delivery_success_batches = count(successful HTTP-200 delivery batches)
```

For Suricata stats:

```text
heartbeat/readiness processing remains at current cadence
latest valid capture_kernel_packets
a latest capture_kernel_drops
latest capture_kernel_ifdrops if present
```

The latest safe values are attached to the existing 60-second sensor metrics summary.

If no valid Suricata stats were observed in the window:

```text
omit those fields
```

Never emit synthetic zero.

## 9.3 Events that remain immediate

Aggregation MUST NOT delay or suppress:

```text
sensor start/stop
runtime/source state transition
capture/preflight failure
raw parser failure
Suricata/EVE failure
fingerprint_delivery_retry
fingerprint_delivery_rejected / permanent reject
spool capacity/overflow fault
stale-drop/eviction fault when emitted as a fault transition
security/config/TLS/credential failure
unexpected exception/fatal path
```

## 9.4 Shutdown / crash

Orderly shutdown emits one final bounded routine summary before the final stopped event when counters are non-zero.

Process crash may lose the in-memory routine telemetry aggregate.
This is permitted because it is explicitly non-authoritative operational telemetry.
No evidence/source-health event is derived from the aggregate.

## 9.5 Privacy

No new telemetry field may contain:

```text
MAC
IP
DNS/SNI
raw payload
event UUID
Bearer token
URI with sensitive identity
```

Only bounded counters/gauges and already admitted runtime identifiers are allowed.
