## 1. Проблема

В Admin UI → **Devices → устройство** блок **Current Device Context** иногда показывает `Current Device Context unavailable. The portal remains operational. Retry manually later.` Обновление страницы обычно помогает.

**Проверено на новом сервере `captiv-prod` (`192.168.0.99`):** NPM зафиксировал **30** вызовов `GET /admin/api/v1/sites/{site_id}/devices/{device_id}/current`: **24× HTTP 200** и **6× HTTP 503** (16–17 октября). Иногда рядом возникали 503 в Devices list/detail и Protocol Intelligence. Current State продолжал собирать полные успешные циклы; целостность SQLite `quick_check=ok`; разовое прямое чтение 106 устройств успешно. Следовательно, проблема **периодическая**, окончательная причина **ещё не доказана**.

**Основной кандидат:** `app/admin_web/device_gateway.py`, метод `_open()` открывает SQLite `timeout=0.0`, а gateway гасит исходное `sqlite3.Error` в общий `AdminDeviceSourceError`. Это может давать мгновенный отказ при краткой занятости SQLite. **Не считать гипотезу доказанной без теста.**

## 2. Задание кодеру

1. **Воспроизвести** на синтетических SQLite/WAL fixture краткий конфликт чтения с writer/checkpoint. Проверить именно цепочку `routes.py` → `query_service.py` → `device_gateway.py` → SQLite. Подтвердить, что воспроизводимый 503 относится к `busy/locked` (либо показать иной установленный источник).
2. **Исправить минимально** подтверждённую причину. Если виноват `timeout=0.0`, применить **короткое, конечное ожидание** блокировки SQLite, строго не выходя за действующий общий `QueryDeadline`. Без бесконечных повторов, повышения глобальных лимитов, новых фоновых задач, лишних опросов Omada и ослабления fail-closed. Никаких изменений SQLite durability/WAL/checkpoints.
3. **Добавить безопасную диагностику** для 503: внутренний тип (`sqlite_busy`, `query_deadline`, `source_unavailable`, `integrity_failure`, `concurrency_limit` и т.п.) и ограниченное время запроса. **Не логировать** MAC, IP клиентов, device_id, SQL-параметры, cookies, токены, ключи или персональные данные; внешний API/error schema не менять.
4. **Тесты:** короткая блокировка заканчивается успешным ответом в рамках deadline; длительная — корректным ограниченным отказом; invalid schema/identity — прежний fail-closed; конкуренция — корректный 429 при превышении слотов; корректные Device list, detail, inventory-summary, current context и Protocol Intelligence не регрессируют. Прогнать релевантную существующую Admin suite.
5. Если причина не подтверждена и тест не воспроизводится — **не менять таймаут наугад**. Сдать только тесты/диагностику и результат `ROOT_CAUSE_HOLD` для решения Tech Lead.
