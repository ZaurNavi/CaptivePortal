## Полевое обнаружение №1 — Captive Portal HTTP и HTTPS у Hestia не эквивалентны

Фактическая Hestia-конфигурация:

```text
captivportal-navi.duckdns.org:80
    Hestia nginx
      → http://192.168.0.202:8080
      → Apache path

captivportal-navi.duckdns.org:443
    Hestia nginx
      → http://127.0.0.1:8088
      → CaptivePortal Flask app
```

Поэтому текущая production semantics:

```text
Direct Hestia HTTP /
→ 200
```

а через NPM с task-prescribed fixed HTTPS upstream:

```text
Client HTTP
  → NPM
  → HTTPS Hestia:443
  → Flask :8088
  → 400
```

Фактическая parity:

```text
                      Direct Hestia     Via NPM fixed HTTPS upstream

Captive Portal /          200                        400
Cloud /                   302                        302
VPN Web /                 200                        200
```

Таким образом для Captive Portal фиксированный `NPM → Hestia:443` меняет HTTP behavior ещё до cutover.

Это конфликтует с A8 principle:

> сменить Edge, а не одновременно изменить поведение сайтов.

## Полевое обнаружение №2 — client IP теряется на втором proxy hop

NPM корректно передаёт:

```nginx
proxy_set_header Host              $host;
proxy_set_header X-Forwarded-Proto $x_forwarded_proto;
proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
proxy_set_header X-Real-IP         $remote_addr;
```

Но Hestia затем для Captive Portal делает:

```nginx
proxy_set_header X-Real-IP       $remote_addr;
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
```

После добавления NPM:

```text
Hestia $remote_addr = 192.168.0.99
```

CaptivePortal использует:

```python
ProxyFix(
    x_for=1,
    x_proto=1,
    x_host=1,
    x_port=1,
)
```

и runtime действительно использует `request.remote_addr`, в том числе CAPPORT/auth/session-related paths.

Field proof:

```text
Direct current path:
client_ip = 192.168.0.106
scheme    = https
host      = captivportal-navi.duckdns.org

Via NPM:
client_ip = 192.168.0.99
scheme    = https
host      = captivportal-navi.duckdns.org
```

То есть:

```text
Host preservation      = PASS
path/query             = PASS
client IP preservation = FAIL
```

## Полевое обнаружение №3 — Hestia имеет технически чистый способ восстановить client IP

Hestia nginx собран с:

```text
--with-http_realip_module
```

и поддерживает trusted-proxy модель.

Минимальный кандидат:

```nginx
set_real_ip_from 192.168.0.99;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

То есть доверять forwarded client address только соединениям непосредственно от NPM.

Hestia-generated domain configs также имеют per-domain include hooks:

```text
nginx.conf_*
nginx.ssl.conf_*
```

поэтому потенциально это можно реализовать без прямого редактирования autogenerated main vhost config.

**Но решение о scope — global Hestia trust vs per-domain trust — должен дать Architect.**

## Нужное архитектурное решение №1 — upstream scheme

Просьба пересмотреть обязательность:

```text
NPM → HTTPS → Hestia:443
```

для **всего** входящего HTTP/HTTPS трафика.

Полевой кандидат:

```text
incoming HTTP
  → NPM
  → Hestia HTTP :80

incoming HTTPS
  → NPM
  → Hestia HTTPS :443
```

концептуально:

```nginx
upstream scheme = incoming frontend scheme
```

При этом остаются неизменными:

```text
upstream destination = Hestia internal IP
public FQDN as upstream = forbidden
Host = public FQDN
HTTPS SNI = public FQDN
```

Это сохраняет существующие Hestia HTTP/HTTPS vhost semantics, включая Captive Portal.

Нужно дать явный verdict:

```text
OPTION A:
scheme-preserving upstream разрешён/обязателен

либо

OPTION B:
fixed HTTPS upstream остаётся обязательным,
и Architect определяет другой способ воспроизвести Captive Portal HTTP semantics.
```

SysAdmin не должен самостоятельно выбирать между A и B.

---

## Нужное архитектурное решение №2 — trusted proxy / real client IP

Нужно определить контракт:

```text
NPM 192.168.0.99
  = единственный новый trusted upstream proxy для Hestia
```

и где должна происходить canonicalization client IP:

```text
NPM → Hestia real_ip module → existing backend/application chain
```

или другой явно заданный вариант.

Просьба определить:

```text
1. допустим ли set_real_ip_from 192.168.0.99;
2. real_ip_header = X-Forwarded-For или другой header;
3. real_ip_recursive on/off;
4. global scope или только три migrating vhost;
5. должен ли X-Real-IP после Hestia содержать canonical client IP;
6. должен ли X-Forwarded-For сохранять полную proxy chain;
7. считать ли изменение CaptivePortal ProxyFix запрещённым в рамках этого TASK.
```

Предпочтительный принцип по результатам field test:

```text
Application code / ProxyFix НЕ менять,
если client-IP semantics можно восстановить на Hestia proxy layer.
```

## Нужное архитектурное решение №3 — X-Forwarded-Proto

Сейчас при fixed HTTPS upstream Hestia естественно видит HTTPS независимо от того, был frontend request HTTP или HTTPS.

Нужно определить authoritative source:

```text
browser/client scheme
```

а не:

```text
NPM → Hestia transport scheme
```

Если принимается scheme-preserving upstream, этот вопрос в основном решается естественно.

Если fixed HTTPS upstream сохраняется, Architect должен задать точный trusted-header contract для передачи original frontend scheme через два proxy hops.

---

## Security constraint

Нельзя просто доверять `X-Forwarded-For` от любого клиента.

Trust должен быть связан именно с:

```text
source proxy = 192.168.0.99
```

Иначе внешний клиент сможет spoof client identity.
