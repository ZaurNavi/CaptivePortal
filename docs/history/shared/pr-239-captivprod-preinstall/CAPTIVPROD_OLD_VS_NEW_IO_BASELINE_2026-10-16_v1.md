# CAPTIV-PROD — сравнительный baseline I/O старого и нового Portal

**Документ:** `CP-PERF-IO-BASELINE-20261016`  
**Версия:** 1.0  
**Дата измерения:** 2026-10-16  
**Статус:** READ-ONLY, production observation, baseline до переноса всех AP  
**Назначение:** контрольная точка для повторного сравнения после миграции всех AP на новый Omada/CaptivPortal.

## 1. Краткий результат

По независимым 60-секундным выборкам новый физический `captiv-prod` (`192.168.0.99`) практически не испытывал дисковой нагрузки. Старый Portal в VM (`192.168.0.202`) выполнял больше операций, имел высокие задержки I/O и почти постоянно занятый виртуальный системный диск. **Это сравнение фактических производственных состояний, а не A/B тест одинаковой нагрузки:** различались перечни служб, данные, количество обслуживаемых клиентов и тип хранилища.

| Метрика за 60 с | Новый `.99` | Старый `.202` | Различие |
|---|---:|---:|---:|
| Чтение + запись, операций | 1 285 | 8 119 | Старый ×6,32 |
| Записи, операций | 1 282 | 4 554 | Старый ×3,55 |
| Чтения, операций | 3 | 3 565 | Не сопоставлять без учёта cache и нагрузки |
| Объём записи | 8,852 МиБ | 46,046 МиБ | Старый ×5,20 |
| Write await | 0,758 мс | 117,465 мс | Старый ×155 |
| Занятость устройства | 1,200% | 96,557% | Устройства разных уровней |
| CPU busy | 3,55% | 33,55% | Старый существенно выше |
| CPU iowait | 0,15% | 57,36% | Старый ждёт I/O |
| I/O PSI some (суммарное stall-время в течение замера) | 0,125 с | 42,647 с | Старый существенно выше |

### Методика

Из Linux собраны снимки **до** и **после** интервала, с секундным отслеживанием пиков:

- `/proc/diskstats`: завершённые I/O, сектора, задержки, время занятости и weighted IO time;
- `/proc/stat`: доли busy, user, system, iowait и idle CPU;
- `/proc/pressure/io`, `/proc/pressure/cpu`, `/proc/pressure/memory`: stall-time;
- `/proc/meminfo`: available, dirty, writeback, swap;
- `/proc/<PID>/io` и `/proc/<PID>/stat`: I/O процессов и CPU ticks; процессы сопоставлялись по PID и starttime.

Все измерения read-only; сервисы, SQLite, Omada, network, firewall и Git не менялись. Скрипты измерения писали только собственный результат в домашний каталог администратора.

**Уровни учёта:** `sda` и `vda` показывают завершённые запросы соответствующих базовых блочных устройств; `dm-0` показывает те же операции на слое LVM. **Не складывать их.** Для VM `vda` не равен физическому I/O HDD гипервизора. `syscr/syscw` — логические системные вызовы, а не физические операции.

### Исправление ошибки в исходном подсчёте flush

В первоначальном скрипте показатель `flush_ops` по ошибке брался из `vals[16]` массива значений `/proc/diskstats` (индексация с нуля); это **flush milliseconds**, а не завершённые операции flush. Количество завершённых flush находится в `vals[15]` для соответствующего 17-польного формата. Поэтому указанные в устном отчёте **252** и **3 569** **не являются количеством flush**. Количество завершённых flush за исходные интервалы достоверно не зафиксировано и здесь указано как `N/A`. Не использовать эти два числа в будущих расчётах коэффициентов. Для следующих измерений сохранять исходные строки `/proc/diskstats` и раздельно считывать `flush_completed` и `flush_time_ms`, предварительно проверив формат полей ядра.

## 6. Выводы и ограничения причинности

1. Старый `vda` демонстрировал признаки насыщенной дисковой подсистемы: `96,557%` busy, очередь `12,4229`, write await `117,465 мс`, IO PSI some `42,647 с` за минуту.
2. Новый физический SSD в этот же период проекта дал `1,200%` busy, очередь `0,0204`, write await `0,758 мс`, почти нулевые чтения и низкий CPU iowait.
3. Старый сервер выполнял больше фоновых задач (Fingerprint, Traffic Projection, Network Metadata, Recognition), работал с другой нагрузкой и собственной историей данных. Нельзя приписывать всё улучшение только изменению CaptivePortal.
4. Нельзя из данных VM `vda` определить физическую загрузку HDD/SSD гипервизора; для этого нужны показатели уровня hypervisor и соседних VM.
5. Транзакции SQLite, число `COMMIT`/`fsync` и checkpoint-операции **напрямую не посчитаны**. Исследование не доказывает причину каждой записи; это baseline для следующего причинного анализа.

## 7. План повторного сравнения после переноса всех AP

При полном переносе на Captiv-Prod провести **тот же 60-секундный read-only замер** (а также отдельный 5–15-минутный для устойчивости, не смешивая показатели). Обязательно фиксировать:

- UTC и локальные временные границы; версию Portal/Omada и работающие сервисы;
- количество online AP; количество online гостей; авторизации, визиты и события за интервал (как контекст нагрузки);
- строки `/proc/diskstats` в начале и конце, включая правильно декодированные `flush_completed` и `flush_time_ms`;
- CPU busy/user/system/iowait/idle, 1-секундные пики; RAM available, активность swap;
- read/write operations, read/write MiB, average await, disk busy, queue depth по физическому/виртуальному устройству отдельно;
- PSI IO/memory stall total и значения `avg60`;
- `/proc/<PID>/io`: Portal, Omada, MongoDB, Fingerprint, projection services, journald;
- особенности workload: сохранённые/новые AP, активные SSID/VLAN, число клиентов, интенсивность трафика.
